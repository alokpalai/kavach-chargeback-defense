# Model card — Kavach chargeback detector

Numbers here are generated by `scripts/report.py` into [`reports/metrics.json`](reports/metrics.json).

---

## Model details

| | |
|---|---|
| Type | LightGBM gradient-boosted trees, binary objective |
| Size | 903 trees, 64 leaves, learning rate 0.05 |
| Input | 435 columns — IEEE-CIS transaction + identity, plus derived `hour`, `dayofweek`, `has_identity` |
| Output | Calibrated-in-rank probability of chargeback fraud |
| Seed | 42 |
| Selection | Early stopping on validation PR-AUC, patience 100 |

**No `scale_pos_weight`.** The reflex fix for a 3.5% base rate is class reweighting. It improves ranking metrics and destroys the probability *scale* — and the entire decision layer compares `p` against an absolute threshold derived from rupees. Imbalance is handled at the threshold, not by distorting the model.

---

## Intended use

**In scope.** Merchant-side risk scoring of card-not-present e-commerce transactions at authorisation, to route an order to approve, step-up authentication, or manual block. Decision support for a fraud operations team.

**Out of scope.**

- **Credit or lending decisions.** This model estimates chargeback risk on a single transaction, not creditworthiness, and must never be repurposed as a credit signal.
- **Profiling individuals.** Scores describe transactions, not people. No score should follow a customer as a durable label.
- **Fully autonomous blocking at scale** without a review path. The block band is 77.7% precision, which means roughly one in four blocked orders is a real customer.
- **Any offensive application.** The repository contains no capability to generate, test, or evade fraud controls, and none should be added.

## Training data

| | |
|---|---|
| Source | [IEEE-CIS Fraud Detection](https://www.kaggle.com/c/ieee-fraud-detection) (Vesta Corporation, via Kaggle) |
| Training rows | 410,601 — days 1–120 |
| Validation rows | 58,776 — days 120–140 |
| Test rows | 78,542 — days 155–183 |
| Discarded | 42,621 — days 140–155, label-latency embargo |
| Label | `isFraud`, a chargeback-derived flag |
| Base rate | 3.50% overall; 3.51 / 3.52 / 3.53% across train / val / test |

Identity data (device, browser, OS) is present on only **24.4%** of transactions. It is left-joined, never inner-joined: the missingness is itself signal, and dropping unmatched rows would train the model on a population that does not exist in production. A `has_identity` flag makes that explicit to the model.

## Cost model

Every rupee figure derives from these assumptions, all declared in `src/kavach/config.py`:

```
C_false_negative = amount + ₹1,500 dispute fee + ₹300 ops handling
C_false_positive = 0.25 × amount + ₹500 expected churn
step-up:  8% of good customers abandon;  85% of fraudsters fail the challenge
currency: IEEE-CIS amounts assumed USD, converted at ₹88
```

These are **assumptions, not measurements**. A merchant deploying this must replace them with their own margin, dispute fees, and challenge pass-rates. The sensitivity analysis (16 combinations of the two 3DS rates) shows the *policy ordering* is stable across a wide range; the absolute rupee figures are not.

## Known limitations and failure modes

### Selection bias — structural, unfixable

A blocked order never ships, never gets disputed, and therefore **never produces a label**. Precision and recall are measured only on traffic the historical system approved. A model deployed on its own decisions progressively stops observing the population it rejects.

Consequences to state plainly:

- Reported precision should be read as an **upper bound**.
- The block band cannot be validated from production data alone. It needs a manual-review sample, or a small randomised approve-anyway holdout, to estimate its true precision.
- Retraining on post-deployment data will inherit and amplify the bias unless that holdout exists.

This affects every fraud model in production anywhere. Naming it is the honest minimum; the mitigation is a holdout, and that is a business decision about how much fraud a merchant will knowingly let through to keep its measurements valid.

### Fairness

IEEE-CIS contains no protected attributes — no age, gender, ethnicity, or precise location. **We therefore cannot measure disparate impact, and do not claim there is none.** Address (`addr1`) and email domain are in the feature set and are plausible proxies for geography and socioeconomic status. Any real deployment must run a disparate-impact audit against attributes the merchant actually holds. Absence of evidence here is not evidence of absence.

### Distribution shift

The model is trained on a 120-day window and tested 15+ days later. Fraud is adversarial and non-stationary: patterns move, and the test PR-AUC of 0.5296 against a validation PR-AUC of 0.6816 already shows meaningful decay across a 15-day gap. Expect degradation and monitor for it. Retraining cadence should be at least monthly, gated on drift monitoring rather than the calendar.

### Hub features

The ring experiment demonstrated that high-cardinality-anchor features can silently encode **platform traffic volume rather than the intended signal**. A planted control (`P_emaildomain × card1`, expected to be useless) ranked second in importance among ring features. Any future feature keyed on a hub entity needs the same control before it is trusted.

### Currency

The dataset does not state its unit. USD is the community consensus, not a fact. All rupee figures scale linearly with `USD_TO_INR`.

### Geographic scope

IEEE-CIS is US e-commerce. Indian traffic differs in instrument mix, ticket size, and regulation — notably RBI's AFA mandate, which means the step-up lever already exists on domestic card payments. The cost framework transfers; the trained weights do not.

## Maintenance

- `pytest` gates the leakage guards on every push; a split that overlaps or an embargo that closes fails the build.
- `scripts/report.py` regenerates every published number. Any metric in the README not reproducible from that script should be treated as stale.
- Monitoring in production should track: score distribution drift (PSI), block-band manual-review precision, actual chargeback rate against the VDMP threshold of 0.65%, and step-up abandonment against the assumed 8%.
